# 校园委托平台 · 1.0 MVP 目标文档

> **文档状态**：目标稿（定义 1.0 版本的业务范围与能力边界，作为后续迭代与验收的目标）
> **版本**：1.0
> **更新日期**：2026-08-01
> **范围**：信息撮合 + 信用账本 + 流程协调，不碰资金、不担交易风险

---

## 一、项目业务能力总览

### 1. 服务对象与面向对象

- **服务对象**：校园封闭 / 半封闭社群（在校生、教职工、校园商户 / 后勤人员）
- **平台角色**：信息撮合器 + 信用账本 + 流程协调员（不碰资金、不担交易风险）

### 2. 对外提供的核心业务流程

> 发布委托 → 信息匹配 / 接单 → 双方确认联系 → 履约打卡 → 评价反馈 → 自动归档

流程设计遵循**轻操作、强留痕、软推进**原则：每一步仅保留必要动作，超时未操作则由系统自动推进，绝不阻塞任务。

### 3. 解决的核心业务痛点

| 痛点 | 平台解决方式 |
| :--- | :--- |
| 「找人难、信息散」（微信群刷屏、找不到靠谱人） | 结构化发布 + 按距离 / 信用智能曝光，告别「海投群聊」 |
| 「信任弱、怕被坑」（陌生人交易、物品交接无保障） | 校园实名背书，多维信用展示，用可量化的口碑替代「盲目信任」 |
| 「流程易断、任务悬停」（接了不办、办了不评、最后不了了之） | 节点超时自动推进 + 24 小时默认评价闭环，任务永不「卡死」 |
| 「纠纷无解、平台难担责」（无资金托管、无法直接赔付） | 信用杠杆 + 流程冻结 + 学生志愿调解，用资格限制替代「金钱赔付」 |

## 二、细分业务能力总览

### 1. 身份准入与信任基座

**核心能力**：分阶梯实名认证（学号 / 工号 / 校园卡核验），生成基础信任身份；后续可无缝对接教务系统实现自动认证。

- **支持场景**：学生代取快递、老师文件代送、跨校区物品传递等常规校园委托。
- **不支持场景**：非校园身份（校外人员）、无实名信息的匿名发布 / 接单。

### 2. 任务发布与智能曝光

**核心能力**：场景化模板一键发布（代买 / 代取 / 代排队 / 代送）；信用分决定任务曝光权重，信用高者任务靠前显示，信用低者自然沉底。

- **支持场景**：日常跑腿、紧急代办、跨楼宇 / 跨校区委托。
- **不支持场景**：复杂定制服务（如需长时间陪护、专业维修）、超出校园安全红线的高危物品代送。

### 3. 履约协同与防断流推进

**核心能力**：仅设**已联系、已取件、已送达**三个轻节点；支持拍照 / 定位打卡（非强制但影响信用）；任一端超时未操作，系统自动推进至下一状态。

- **支持场景**：标准跑腿、短时交接（如食堂代买、快递代取）。
- **不支持场景**：需多段中转的复杂物流、需长时间跟踪的异步任务（如「明天下午去某地等我」）。

### 4. 信用评价与画像沉淀

**核心能力**：1 分钟快捷评价（星级 + 标签）；24 小时未评自动按中性好评归档；信用分由活跃度、准时率、评价口碑、合规记录多维计算，**仅展示个人状态，不公开排名**。

- **支持场景**：服务反馈沉淀、跑腿人 / 委托人双向画像生成、优质用户激励。
- **不支持场景**：恶意差评报复（系统拦截非常规评价）、实时信用分排名竞争（避免校园社交压力）。

### 5. 风控调解与争议处理

**核心能力**：脱敏联系方式（接单后解密一次）；争议发起后任务冻结；学生志愿者 / 管理员介入调解；调解结果仅调整信用分与功能权限，不涉及资金。

- **支持场景**：物品交接纠纷、服务态度投诉、爽约 / 失联处理。
- **不支持场景**：要求平台先行赔付、涉及法律层面的大额财产损失追偿、非平台流程内的私下交易纠纷。

## 三、业务价值能力总结

### 1. 对用户：安全、省心、可预期

- 告别微信群「盲找」，信息集中、匹配高效。
- 不看头像看信用，历史履约数据透明，降低决策成本。
- 流程不卡壳，系统自动兜底推进，省时省力。

### 2. 对校园管理：数字化、可治理、低风险

- 将原本分散在社交软件里的灰色跑腿阳光化、线上化，便于安全与秩序管理。
- 通过数据看板掌握校园高频需求热点（如某快递点高峰时段、某教学楼文件流转频次），为后勤服务优化提供依据。
- 不碰资金、不承担赔付责任，平台风险可控，合规门槛低。

### 3. 对平台自身：轻资产启动、信任飞轮自转

- 以信息撮合 + 信用账本起步，规避金融牌照与资金托管压力。
- 信用分与曝光权重挂钩，形成「好评 → 更多订单 → 更高信用」的正向循环。
- 为后续引入支付、场景保险、校园服务生态留出平滑升级接口。

## 四、待确认信息（需管理层 / 运营团队决策）

| 待确认项 | 说明与建议 |
| :--- | :--- |
| ★1. 认证对接节奏与预算 | 初期是否采用「人工后台审核」过渡？教务系统 API 对接的排期、费用与数据授权范围需提前与校方信息化部门确认。 |
| ★2. 信用惩罚力度与申诉规则 | 爽约 / 纠纷扣多少分？封禁几天？谁负责审核申诉？建议初期设置「可申诉、有宽限期」的温和策略，避免学生抵触。 |
| ★3. 争议调解团队构成 | 是否招募学生会 / 志愿者组成「校园跑腿调解组」？需明确响应时效（如 24 小时内介入）与调解权限边界。 |
| ★4. 隐私展示尺度 | 个人名片展示到「学院 + 年级」还是仅显示 L2 认证校园用户？需结合《个人信息保护法》与校方意见定稿。 |
| ★5. 冷启动运营策略 | 无资金激励下，如何吸引首批种子用户？建议采用「信用徽章 + 任务优先曝光 + 学期末服务积分兑换」等轻激励手段。 |
| ★6. 未来资金引入路径 | 若后续需上线支付 / 托管，需提前评估合规路径（如对接持牌支付机构、校园一卡通系统）；当前架构已预留对接接口。 |

## 给管理者的核心提示

本系统不靠「管钱」控流程，而是靠**信用 + 履约**。校园是天然的信任放大器，把每一次发布、接单、评价都转化为可累积的信用资产，配合系统自动推进机制，即可在零资金风险的前提下，跑通高可用的服务闭环。当前阶段聚焦**信息流 + 信用流双轮驱动**，待用户习惯养成与校方数据打通后，可平滑扩展至交易层。如需输出各模块的交互原型说明或运营 SOP，可随时提供。
