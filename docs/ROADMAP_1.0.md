## 一、差距分析：现状 vs MVP 1.0

MVP_1.0 定义五大能力区，其中「核心闭环」为 P1（信用评价、智能曝光、防断流），「身份准入、风控调解」为 P2（延后）。下表为当前代码实现与 MVP 目标的对照。

| MVP 能力点 | 现状 | 归属 |
| :--- | :--- | :--- |
| 任务全流程（发布 → 审核 → 接单 → 三节点打卡 → 完成 → 评价） | ✅ 已实现（10 种任务状态 + `TaskUpdates` 已联系/已取件/已送达） | P1 |
| 24h 自动评价归档 | ✅ 已实现（`TaskAutoReview` 定时任务，默认 24h） | P1 |
| 信用档案展示 | ⚠️ 仅有统计（接单数、平均分、好评率），**无信用分** | P1 |
| 信用分计算 | ❌ 缺失 | P1 |
| 信用加权曝光 | ❌ 缺失 | P1 |
| 履约节点超时自动推进 | ❌ 缺失（仅有过期清理 `TaskOverDue`） | P1 |
| 评价护栏（恶意差评/敏感词） | ⚠️ 敏感词模块已有，未接入评论过滤 | P1 |
| 分阶梯实名认证 | ❌ 缺失 | P2 |
| 风控调解/争议处理 | ❌ 缺失 | P2 |
| 信用惩罚与申诉 | ❌ 缺失 | P2 |

**结论**：核心闭环的缺口集中在三条线上 —— **信用分计算 → 信用加权曝光**（依赖链），以及**节点超时自动推进**（独立线）。P2 两区整体后置。

## 二、构建顺序：M1 → M2 → M3 → M4

依赖关系：`M1 信用引擎` 是 `M2 智能曝光` 的前置；`M3 防断流`、`M4 评价护栏` 独立，可与 M1/M2 并行，但按 M1 → M4 顺序推进，确保每步可独立验收。

### M1 信用引擎（地基，依赖：无）

- 新建 `CreditScoreService`，对外暴露信用分查询。
- 定义可插拔策略接口 `CreditCalculator`：v1 用简单算法，后续升级多维算法时**不改调用方**。
- **v1 算法（先简单后升级）**：
  `信用分 = 60% × 均分归一化 + 40% × 完成率`，无历史数据时返回默认分（建议 60）。
  - 均分归一化：`平均评分 / 5 × 100`（无评分按 3 星即 60 分计）。
  - 完成率：`已完成接单数 / 已确认接单数`（无接单按 100% 计）。
- 计算方式：**按需 SQL 聚合**（复用现有 mapper 聚合能力，不动表结构）；预留「定时预计算 + 缓存」升级位（对应架构里的 Redis 缓存位）。
- 展示：`CreditProfile.vue` 增补信用分展示；新增或复用 `/credit` 接口返回信用分。

**验收要点**：老用户/新用户均能拿到一个稳定信用分；策略接口存在；换算法不改 Controller。

### M2 智能曝光（依赖：M1）

- 任务大厅查询排序键改为 `(信用分 DESC, 创建时间 DESC)`。
- 信用分获取复用 M1 的 `CreditScoreService`。
- **冷启动取舍**：信用数据积累初期排序效果不明显，属运营问题，不作为架构阻塞；后续可平滑升级为「信用分 + 时间衰减」混合权重（预留升级位）。

**验收要点**：大厅列表能按信用分降序呈现；同分任务按时间倒序；排序对接口/前端无破坏性变更。

### M3 防断流（依赖：无，可与 M1/M2 并行）

- 新增 `TaskAutoAdvance` 定时任务（复用 `@Scheduled` 基建，参考 `TaskOverDue` / `TaskAutoReview`）。
- **规则 1 · 节点超时自动推进**：接收者当前节点超时未打卡，系统自动推进至下一节点，并写入一条 `TaskUpdates` 留痕（`type=AUTO_ADVANCE`，与手动打卡区分，供后续信用/审计使用）。
- **规则 2 · 完成超时自动确认**：ACCEPTED 状态下三节点均已打卡但发布者超时未确认完成，系统自动置 `COMPLETED`，进入既有评价闭环。
- 超时时长走 `application.yml` 配置（建议：节点 6h，完成确认 24h），演示时可调小快速触发。
- 自动推进与「过期清理 `TaskOverDue`」「自动评价 `TaskAutoReview`」互不冲突：三者在不同状态分支各自兜底。

**验收要点**：超时未打卡节点会被自动推进且留痕；超时未确认会进入评价；配置可调。

### M4 评价护栏（已纳入 P1，依赖：无）

- 评论内容接入现有敏感词过滤（`SensitiveWordController` 模块）。
- 互评一次性校验：同一任务双方各至多一条评价（补齐边界，防重复）。
- 评分范围校验（1–5）与异常评价拦截位。

**验收要点**：含敏感词评论被拦截；同任务不可重复评价。

## 三、P2 延后清单（1.0 之后）

| 能力 | 说明 | 预留钩子 |
| :--- | :--- | :--- |
| 分阶梯实名认证 | 学号/工号/校园卡核验，L1/L2 身份分层 | 用户表预留认证字段位 |
| 风控调解/争议 | 争议发起、任务冻结、志愿者/管理员介入 | 任务状态预留冻结位；`DelegateAuditRecords` 模块（当前注释态）可复用 |
| 信用惩罚与申诉 | 爽约/纠纷扣分、封禁、申诉审核 | M3 的 `AUTO_ADVANCE` 留痕接入合规维度；`CreditCalculator` 换多维算法 |
| 恶意差评策略 | 非常规评价拦截、申诉后复核 | M4 拦截位扩展 |

## 四、开放决策（已确认，2026-08-01）

| 决策项 | 确认值 | 备注 |
| :--- | :--- | :--- |
| 信用分初始默认值 | 60 分 | 无数据用户不归零，避免冷启动埋没 |
| 均分 / 完成率权重 | 60% / 40% | v1 固化，v2 由 `CreditCalculator` 重算 |
| 节点超时时长 | 6h | `application.yml` 可调 |
| 完成确认超时时长 | 24h | 与自动评价 24h 对齐 |
| `AUTO_ADVANCE` 是否计入合规维度 | 暂不计入 | P2 引入惩罚机制时再评估 |
| M4 评价护栏 | 纳入 P1 | 敏感词过滤 + 互评一次性校验为 P1 范围；恶意差评拦截策略归 P2 |
