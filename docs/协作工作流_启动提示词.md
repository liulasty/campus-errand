## DSL 用例编写规范（踩坑总结，务必遵守）
1. expect 是字面量（不做模板渲染），不能放 ${{...}}。动态比较用 `SELECT 1 AS ok ... WHERE <含 ${{...}}>`，expect 固定 {ok:1} 或 {cnt:N}。
2. outputs 提取不支持数组路径（data.records[0].id 取不到）；但 api/body/sql 里可用 `steps.X.body.data.records[0].taskId`（render 用 lodash.get）。
   取 taskId：create_draft 步骤 `outputs:{taskId: data}`（后端 create 已返回 taskId），后续用 ${{steps.create_draft.output.taskId}}。
3. query 参数直接拼在 api 字符串（runner 忽略 steps 的 query 字段）：/path?pageNum=1&status=ONGOING。
4. SQL 字符串值必须加单引号：u.Username = '${{steps.X.body.data[0].ownerName}}'。
5. 日期用 ISO-8601：PublishDTO 的 end 必须未来，如 "2099-12-31T23:59:59Z"。
6. 唯一测试数据用 ${{run.id}}（用户名/描述/category 名）保证可重跑幂等。
7. 状态列：DB 存英文 dbValue（ONGOING/ACCEPTED），API 返回中文 webValue（委托发布中/已接收）；DB 断言用英文。
8. 敏感词库：代考/作弊/诈骗；任务创建与评价已做敏感词校验。
9. 清理：测试数据按「环境不清理」积累；用例 cleanup 可引 steps 删自己建的资源。

2. 修完 → 重新输出/更新用例 → 重启后端 → 告知可复测。
3. 不要自行跑测、不要擅自重跑、不要预跑冒烟。
